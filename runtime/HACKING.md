# [Go 源代码破解 - `runtime` 包](https://go.dev/src/runtime/HACKING)

这是一份动态文档，有时会过时。其目的是阐述在 Go 运行时环境中编程与编写普通 Go 代码有何不同。它侧重于普遍存在的概念，而非特定接口的细节。

## 调度器结构

调度器管理着运行时环境中普遍存在的三种资源：G、M 和 P。即使您不参与调度器的开发，理解这些资源也至关重要。

### G、M、P

"G"指的就是一个 goroutine，类型为 `g`。当一个 goroutine 退出时，它的 g 对象会被返回到一个空闲的 g 对象池中，以便之后可以被其他 goroutine 重用。

"M"指的是一个操作系统线程，它可以执行用户编写的 Go 代码、运行时代码、系统调用，或者处于空闲状态。类型为 `m`。由于系统调用中可能会阻塞任意数量的线程，因此同一时间可以存在任意数量的 M。

最后，"P"代表执行用户 Go 代码所需的资源，例如调度器和内存分配器的状态。它用类型 `p` 表示。P 的数量恰好为 `GOMAXPROCS`。可以将 P 视为操作系统调度器中的一个 CPU，而 p 类型的内容则类似于每个 CPU 的状态。这里非常适合存放那些需要分片以提高效率，但不需要按线程或 goroutine 划分的状态。

调度器的任务是匹配 G（要执行的代码）、M（执行位置）和 P（执行代码所需的权限和资源）。当 M 停止执行用户 Go 代码时（例如，通过进入系统调用），它会将自身的 P 返回到空闲 P 池。为了恢复执行用户 Go 代码（例如，从系统调用返回后），它必须从空闲池中获取一个 P。

所有 g、m 和 p 对象都是堆分配的，但永远不会被释放，因此它们的内存保持类型稳定。因此，运行时可以避免调度器深处的写屏障。

### getg()和getg().m.curg

要获取当前用户 g，请使用 `getg().m.curg`。

单独使用 `getg()` 会返回当前 g，但如果在系统栈或信号栈上执行，则会分别返回当前 M 的"g0"或"gsignal"。这通常不是你想要的结果。

要确定当前是在用户栈还是系统栈上运行，请使用 `getg() == getg().m.curg`。

## 栈

每个非死的 G 都关联着一个用户栈，用户 Go 代码就执行在这个用户栈上。用户栈初始大小很小（例如 2K），并会动态地增长或缩小。

每个 M 都关联着一个系统栈（也称为 M 的"g0"栈，因为它被实现为一个存根 G），并且在 Unix 平台上还有一个信号栈（也称为 M 的"gsignal"栈）。系统栈和信号栈不能增长，但它们的大小足以执行运行时代码和 cgo 代码（在纯 Go 二进制文件中为 8K；在 cgo 二进制文件中由系统分配）。

运行时代码经常使用 `systemstack`、`mcall` 或 `asmcgocall` 等函数临时切换到系统栈，以执行那些不能被抢占、不能增加用户栈大小或需要切换用户 goroutine 的任务。运行在系统栈上的代码隐式地不可抢占，垃圾回收器不会扫描系统栈。在系统栈上运行时，当前用户栈不用于执行。

### nosplit 函数

大多数函数以一个`序言`开始，该序言会检查栈指针和当前 G 的栈边界，并在栈需要增长时调用 `morestack`。

函数可以标记为 `//go:nosplit`（或汇编中的 `NOSPLIT`），以表明它们不应该执行此序言。这有以下几个用途：

- 必须在用户栈上运行，但不能调用栈增长函数的函数，可能原因有，这会导致死锁，或者因为栈上有未类型化的字。
- 不能在代运行时被抢占的函数。
- 可能在没有有效 G 的情况下运行的函数。例如，在运行时启动早期运行的函数，或者可能从 C 代码（例如 cgo 回调或信号处理程序）进入的函数。

可拆分函数确保栈上有一些空间供 nosplit 函数运行，并且链接器会检查任何 nosplit 函数调用的静态链是否不能超过此边界。

任何带有 `//go:nosplit` 注解的函数都应该在其文档注释中解释为什么它没有进行分割。

## 错误处理和报告

对于用户代码中可以合理恢复的错误，应像往常一样使用 `panic`。但是，在某些情况下，panic 会导致立即发生致命错误，例如在系统堆栈上调用 panic 或在 `mallocgc` 期间调用 panic。

大多数运行时错误是不可恢复的。对于这些错误，请使用 `throw`，它会输出回溯信息并立即终止进程。通常，throw 应传递一个字符串常量，以避免在危险情况下分配内存。按照惯例，在 throw 之前使用 print 或 println 打印更多详细信息，并且消息以"runtime:"为前缀。

对于用户代码可能导致的不可恢复错误（例如，争用映射写入），请使用 `fatal`。

对于运行时错误调试，使用 `GOTRACEBACK=system` 或 `GOTRACEBACK=crash` 运行可能很有用。`panic` 和 `fatal` 的输出与 `GOTRACEBACK` 的描述一致。无论 GOTRACEBACK 是否为真（即等效于 GOTRACEBACK=system），throw 的输出始终包含运行时帧、元数据和所有 goroutine。throw 是否崩溃仍然由 GOTRACEBACK 控制。

## 同步

运行时环境有多种同步机制。它们的语义各不相同，尤其是在与 goroutine 调度器还是操作系统调度器交互方面存在差异。

最简单的机制是`mutex`（互斥锁），它通过`lock`和`unlock`操作。互斥锁应该用于在短时间内保护共享结构。阻塞互斥锁会直接阻塞 M 进程，而无需与 Go 调度器交互。这意味着它可以安全地从运行时环境的底层使用，同时也防止任何关联的 G 和 P 进程被重新调度。`rwmutex`（读写互斥锁）与之类似。

对于一次性通知，可以使用 `note` 函数，它提供了 `notesleep` 和 `notewakeup` 函数。与传统的 UNIX sleep/wakeup 不同，note 函数不会发生竞争条件，因此如果 notewakeup 已经发生，notesleep 会立即返回。note 可以使用 noteclear 函数在使用后重置，但 noteclear 函数不能与 sleep 或 wakeup 函数发生竞争条件。与互斥锁类似，阻塞一个note（通知）会阻塞 M。然而，对通知进行睡眠的方式有所不同：`notesleep` 会阻止任何关联的 G 和 P 的重新调度，而 `notetsleepg` 则类似于阻塞系统调用，允许 P 被重用以运行另一个 G。但这仍然不如直接阻塞 G 高效，因为它会消耗一个 M。

要直接与 goroutine 调度器交互，请使用 `gopark` 和 `goready`。`gopark` 会将当前 goroutine 置于"waiting（等待）"状态并从调度器的运行队列中移除，然后在当前 M/P 上调度另一个 goroutine。`goready` 会将已停放的 goroutine 恢复到"runnable（可运行）"状态并将其添加到运行队列中。

总而言之，
|||Blocks||
|-|-|-|-|
|Interface|G|M|P|
|(rw)mutex|Y|Y|Y|
|note|Y|Y|Y/N|
|park|Y|N|N|

## 原子操作

运行时使用其自身的原子操作包，位于 `internal/runtime/atomic`。这对应于 `sync/atomic`，但由于历史原因，函数名称有所不同，并且运行时还需要一些额外的函数。

一般来说，我们会认真考虑运行时中原子操作的使用，并尽量避免不必要的原子操作。如果对某个变量的访问有时受到其他同步机制的保护，那么这些已经受到保护的访问通常不需要是原子操作。原因有以下几点：

1. 在适当的情况下使用非原子或原子访问可以使代码更具自文档性。对变量的原子访问意味着其他地方可能同时访问该变量。
2. 非原子访问允许自动进行竞争检测。运行时目前没有竞争检测器，但将来可能会添加。原子访问会绕过竞争检测器，而非原子访问则允许竞争检测器检查您的假设。
3. 非原子访问可以提高性能。

当然，任何对共享变量的非原子访问都应该记录下来，解释这种访问是如何受到保护的。

一些常见的混合使用原子和非原子访问的模式包括：

- 主要以读取为主的变量，其更新操作受锁保护。在锁定区域内，读取操作不需要是原子的，但写入操作必须是原子的。在锁定区域外，读取操作必须是原子的。
- 仅在 STW 期间发生的读取操作（在 STW 期间不能进行任何写入操作）不需要是原子的。

也就是说，Go 内存模型的建议仍然适用："不要自作聪明。"运行时的性能固然重要，但其健壮性更为重要。

## 非托管内存

通常，运行时会尝试使用常规堆内存分配。然而，在某些情况下，运行时必须在垃圾回收堆之外的非托管内存中分配对象。如果对象本身就是内存管理器的一部分，或者必须在调用者可能没有 P 的情况下分配对象，则必须这样做。

分配非托管内存有三种机制：

- `sysAlloc` 直接从操作系统获取内存。分配的内存大小是系统页面大小的整数倍，但可以使用 `sysFree` 释放。
- `persistentalloc` 将多个较小的内存分配合并为一个 `sysAlloc`，以避免内存碎片。但是，无法释放 `persistentalloc` 分配的对象（因此得名）。
- `fixalloc` 是一种 SLAB 风格的内存分配器，用于分配固定大小的对象。fixalloc 分配的对象可以被释放，但该内存只能由同一个 `fixalloc 池`重用，因此只能用于相同类型的对象。

一般来说，使用上述任何方法分配的类型都应通过嵌入 `internal/runtime/sys.NotInHeap` 来标记为不在堆中。

分配在非托管内存中的对象不得包含堆指针，除非同时遵守以下规则：

1. 任何从非托管内存指向堆的指针都必须是垃圾回收根。更具体地说，任何指针都必须可以通过全局变量访问，或者在 `runtime.markroot` 中显式添加为垃圾回收根。
2. 如果内存被重用，则堆指针必须在成为垃圾回收根之前进行零初始化。否则，垃圾回收器可能会遇到过时的堆指针。请参阅"零初始化与清零"。

## 零初始化与清零

运行时清零有两种类型，取决于内存是否已初始化为类型安全状态。

如果内存未处于类型安全状态，意味着它可能包含"垃圾数据"（因为它刚刚分配，正在初始化以供首次使用），则必须使用 `memclrNoHeapPointers` 或非指针写入进行零初始化。这不会执行写屏障。

如果内存已处于类型安全状态，并且只是被设置为零值，则必须使用常规写入、`typedmemclr` 或 `memclrHasPointers`。这执行写屏障。

## 链接名约定

```go
//go:linkname localname [importpath.name]
```

`//go:linkname` 指定用于引用本地标识符 (`localname`) 的符号名称 (`importpath.name`)。目标符号名称可以是任意 ELF/macho 等符号名称，但按照惯例，我们通常使用带有包名前缀的符号名称以保持代码的组织性。

`//go:linkname` 的通用性非常灵活，因此为了简化操作，我们定义了三种标准的 `//go:linkname` 指令形式。

尽可能优先使用下文所述的链接名"握手"方式。

### "推送链接名"

"推送"链接名会为本地定义在另一个包中指定一个最终的符号名称。这实际上是将符号"推送"到另一个包中。

```go
//go:linkname foo otherpkg.foo
func foo() {
    // impl
}
```

另一个包需要声明才能使用 Go 中的符号，或者可以直接在汇编代码中引用该符号。通常情况下，这是一个"export linkname"声明（如下所示）。

### "拉取链接名"

"拉取"链接名为对本地声明的引用赋予一个来自其他包的最终符号名称。这实际上是从另一个包中"拉取"该符号。

```go
//go:linkname foo otherpkg.foo
func foo()
```

另一个包只需定义该符号即可，但通常情况下，这是一个"export linkname"定义（如下所示）。

### "导出链接名"

`//go:linkname` 的第二个参数是目标符号名。如果省略，工具链将使用默认符号名。换句话说，这是一个指向自身的链接名。这看似是一个空操作，但实际上表示该符号被"导出"以供其他链接名使用。

```go
//go:linkname foo
func foo() {
    // impl
}
```

当应用于定义时，导出链接名表示另一个包有一个指向该符号的拉取链接名。这会产生以下几个影响：

- 编译器避免为 ABI0 和/或 ABIInternal 生成 ABI 包装器，因此在 Go 中定义的符号可以被另一个包中的汇编代码引用，反之亦然。
- 即使设置了 `-checklinkname=true`，链接器也允许指向该符号的拉取链接名（参见下文"握手"部分）。

```go
//go:linkname foo
func foo()
```

当应用于声明时，导出链接名表示另一个包有一个指向该符号的推送链接名。除了文档之外，它对工具链的唯一影响是编译器将不再要求包中包含 `.s` 文件（通常情况下，当存在没有函数体的函数声明时，编译器会要求包含 .s 文件）。

### 握手

我们始终优先使用`推送链接名`而不是`拉取链接名`。使用推送链接名，定义包知道它正在向另一个包发布 API。另一方面，使用拉取链接名，定义包可能完全不知道这种依赖关系，并可能无意中破坏用户。

链接名的首选形式是在定义包中使用推送链接名，在接收包中使用目标链接名。后者并非严格要求，但可以作为文档。按照惯例，接收包会命名包含源包的符号，以进一步辅助文档编写。

```go
package runtime

//go:linkname foo otherpkg.runtime_foo
func foo() {
    // impl
}

```

```go
package otherpkg

//go:linkname runtime_foo
func runtime_foo()
```

从 Go 1.23 开始，链接器禁止标准库符号使用拉取链接名，除非它们参与握手。由于许多第三方包已经使用了指向标准库函数的拉取链接名，为了向后兼容，作为外部拉取链接名目标的标准库符号必须使用目标链接名，以向链接器表明拉取链接名是可以接受的。

```go
package runtime

//go:linkname fastrand
func fastrand() {
    // impl
}

```

请注意，可以使用 `-checklinkname=false` 标志禁用链接器强制执行。

### 变量

以上所有示例均在函数中使用 `//go:linkname`。虽然也可以在全局变量上使用它，但这非常少见。

变量的定义和声明之间没有明确的界限。通常，只有一侧应该有非零的初始值。这一侧是"定义"，另一侧是"声明"。

两侧应该具有相同的类型，包括大小。但是，如果一侧比另一侧大，链接器会为较大的一侧分配空间。

## 运行时编译器指令

除了"go doc compile"文档中记录的"//go:"指令之外，编译器还支持一些仅在运行时才使用的指令。

#### go:systemstack

`go:systemstack` 指示函数必须在系统栈上运行。这由一个特殊的函数序言动态检查。

#### go:nowritebarrier

go:nowritebarrier 指示编译器，如果后续函数包含任何写屏障，则发出错误。（它不会阻止写屏障的生成；它只是一个断言。）

通常情况下，您需要使用 go:nowritebarrierrec。go:nowritebarrier 主要适用于"最好"不使用写屏障，但并非正确性所必需的情况。

#### go:nowritebarrierrec 和 go:yeswritebarrierrec

go:nowritebarrierrec 指示编译器，如果后续函数或其递归调用的任何函数（直到 go:yeswritebarrierrec）包含写屏障，则发出错误。

从逻辑上讲，编译器会从每个 go:nowritebarrierrec 函数开始遍历调用图，并在遇到包含写屏障的函数时产生错误。这种遍历会在 go:yeswritebarrierrec 函数处停止。

go:nowritebarrierrec 用于写屏障的实现中，以防止无限循环。

这两条指令都用于调度器中。写屏障需要一个活动的 P（`getg().m.p != nil`），而调度器代码经常在没有活动 P 的情况下运行。在这种情况下，对于释放 P 或可能在没有 P 的情况下运行的函数，使用 `go:nowritebarrierrec`；而对于重新获取活动 P 的代码，则使用 `go:yeswritebarrierrec`。由于这些是函数级注解，因此释放或获取 P 的代码可能需要拆分到两个函数中。

#### go:uintptrkeepalive

`//go:uintptrkeepalive` 指令后必须跟一个函数声明。

它指定函数的 `uintptr` 参数可以是已转换为 `uintptr` 的指针值，并且必须在函数调用期间保持其存活状态，即使仅从类型上看，该对象在调用期间似乎不再需要。

此指令类似于 `//go:uintptrescapes`，但它不会强制参数转义。由于栈增长无法识别这些参数，因此必须将此指令与 `//go:nosplit`（在标记的函数及其所有传递调用中）一起使用，以防止栈增长。

从指针到 `uintptr` 的转换必须出现在对该函数的任何调用的参数列表中。此指令用于一些底层系统调用实现。

## 执行跟踪器

执行跟踪器允许用户查看其 goroutine 的执行情况，但它们对于运行时优化也很有用。

### 使用执行跟踪调试运行时问题

执行跟踪包含丰富的运行时信息。它们包含所有 goroutine 调度操作、调度器中花费的时间数据（例如，进程 P 运行但未触发 G）、垃圾回收器中花费的时间数据等等。可以使用 `go tool trace` 或 `gotraceui` 来检查跟踪信息。

跟踪信息对于调试延迟问题尤其有用，尤其是在问题发生时能够立即捕获的情况下。可以考虑使用飞行记录器来辅助调试。

在进行跟踪时启用 CPU 分析。这会将 CPU 分析样本作为带时间戳的事件添加到跟踪信息中，从而让您能够更详细地查看执行过程。如果您发现 CPU 分析样本事件的出现频率与采样频率不匹配，则可能是操作系统或平台占用了进程的 CPU 时间，而您可能并非在调试 Go 问题。

如果您确实被某个问题难住了，使用跟踪器添加新的检测信息可能会有所帮助，尤其是在需要查看事件与其他调度事件之间的关系时。请参阅下一节关于修改执行跟踪器的内容。不过，建议您先使用 debuglog 进行额外的检测，因为它更容易上手。

### 关于修改执行跟踪器的注意事项

执行跟踪器位于文件名以"trace"开头的文件中。执行跟踪格式的解析器位于 `internal/trace` 包中。

如果您计划添加新的跟踪事件，请考虑先进行[跟踪实验](https://go.dev/src/internal/trace/tracev2/EXPERIMENTS.md)。

如果您计划向运行时添加新的跟踪检测，请阅读 [`trace.go`](https://go.dev/src/runtime/trace.go) 文件顶部的注释，特别是其中的不变量部分。

## debuglog

debuglog 是一个功能强大的运行时调试工具。您可以将其视为一个开销极低的 println，几乎可以在运行时的任何位置使用。这些特性在调试代码库中复杂部分的细微问题时尤为重要。println 通常会对代码进行足够的扰动，从而阻止数据竞争的发生，而 debuglog 对执行的干扰则要小得多。

debuglog 会在每个 M 周期将日志消息累积到一个环形缓冲区中，并在某些类型的崩溃发生时，按时间戳顺序输出其内容。如果环形缓冲区已满，则可能会丢失一些消息，在这种情况下，请考虑增加缓冲区大小，或者只使用部分日志。

1. 将 debuglog 检测添加到运行时。不要忘记调用 end！例如：`dlog().s("hello world").u32(5).end()`
2. 默认情况下，debuglog 仅在某些类型的崩溃发生时输出其内容。如果您没有获得任何输出，请考虑增加 `printDebugLog` 的调用次数。
3. 使用 debuglog 构建标签构建要调试的程序。

调试日志的级别比执行跟踪低，而且设置起来也容易得多。
