# [Go垃圾回收器入门](https://go.dev/doc/gc-guide)

## 介绍

本指南旨在帮助高级 Go 用户更好地了解其应用程序的成本，深入剖析 Go 的垃圾回收机制。它还指导 Go 用户如何利用这些知识来提高应用程序的资源利用率。本指南不假设读者具备任何垃圾回收方面的知识，但假定读者熟悉 Go 编程语言。

Go 语言负责管理 Go 值的存储；在大多数情况下，Go 开发者无需关心这些值存储在哪里，或者为什么存储。然而，在实践中，这些值通常需要存储在计算机的`物理内存`中，而物理内存是一种有限的资源。由于内存有限，因此必须谨慎管理并回收内存，以避免在执行 Go 程序时耗尽内存。Go 实现的职责就是根据需要分配和回收内存。

自动回收内存的另一个术语是垃圾回收。从宏观层面来说，垃圾回收器（简称 GC）是一个代表应用程序回收内存的系统，它通过识别哪些内存部分不再需要来实现这一点。 Go 标准工具链提供了一个运行时库，该库随每个应用程序一起发布，并且包含一个垃圾回收器。

请注意，[Go 规范](https://go.dev/ref/spec)并未保证本指南中描述的垃圾回收器的存在，而只是保证 Go 语言本身管理底层值的存储。这种省略是故意的，它使得可以使用截然不同的内存管理技术。

因此，本指南针对的是 Go 编程语言的特定实现，可能不适用于其他实现。具体来说，本指南适用于标准工具链（即 gc Go 编译器和工具）。Gccgo 和 Gollvm 都使用了非常相似的 GC 实现，因此许多概念是相同的，但细节可能有所不同。

此外，本文档会不断更新，以更好地反映 Go 的最新版本。本文档目前描述的是 Go 1.19 的垃圾回收器。

## Go 值存放位置

在深入探讨垃圾回收器 (GC) 之前，我们先来讨论一下哪些内存不需要由 GC 管理。

例如，存储在局部变量中的非指针 Go 值通常根本不会由 Go GC 管理，Go 会安排分配与创建该值所在的[词法作用域](https://go.dev/ref/spec#Declarations_and_scope)绑定的内存。一般来说，这比依赖 GC 更高效，因为 Go 编译器能够预先确定何时可以释放这些内存，并发出相应的机器指令进行清理。通常，我们将这种为 Go 值分配内存的方式称为"栈分配"，因为这些空间存储在 goroutine 栈上。

那些无法通过这种方式分配内存的 Go 值（因为 Go 编译器无法确定其生命周期）被称为逃逸到堆。"堆"可以被视为内存分配的"兜底池"，用于存放所有需要存放的 Go 值。在堆上分配内存的行为通常被称为"动态内存分配"，因为编译器和运行时都很难预先判断内存的使用方式以及何时需要清理。这时就需要垃圾回收器（GC）了：它是一个专门识别并清理动态内存分配的系统。

Go 值需要逃逸到堆的原因有很多。其中一个原因可能是其大小是动态确定的。例如，考虑一个切片的底层数组，其初始大小由一个变量而非常量决定。需要注意的是，逃逸到堆必须具有传递性：如果将对一个 Go 值的引用写入另一个已被判定为逃逸的 Go 值，则该值也必须逃逸。

Go 值是否逃逸取决于其使用上下文以及 Go 编译器的逃逸分析算法。试图精确枚举值何时逃逸是脆弱且困难的：该算法本身相当复杂，并且在不同的 Go 版本之间也会发生变化。有关如何识别哪些值会逃逸以及哪些值不会逃逸的更多详细信息，请参阅[消除堆分配](https://go.dev/doc/gc-guide#Eliminating_heap_allocations)部分。

## 追踪型垃圾回收

垃圾回收可以指代多种不同的内存自动回收方法，例如引用计数。在本文档中，垃圾回收指的是`追踪型垃圾回收`，它通过传递追踪指针来识别正在使用中的（即所谓的"存活"）对象。

让我们更严谨地定义这些术语。

- `对象` —— 对象是动态分配的内存块，其中包含一个或多个 Go 值。
- `指针` —— 指向对象中任何值的内存地址。这自然包括 `*T` 形式的 Go 值，但也包括内置 Go 值的一部分。字符串、切片、通道、映射和接口值都包含 GC 必须追踪的内存地址。

对象和指向其他对象的指针共同构成`对象图`。为了识别存活内存，GC 从`程序的根节点`开始遍历对象图，根节点是指向程序正在使用的对象的指针。局部变量和全局变量都是根节点的例子。遍历对象图的过程称为`扫描`。在 Go 文档中，你可能还会看到对象是否`可达`这个短语，它指的是对象是否能被扫描过程发现。还要注意的是，除了一个例外，一旦内存变为不可达，它就一直保持不可达状态。

这个基本算法是所有追踪型垃圾回收器（Tracing GC）的通用算法。不同追踪型垃圾回收器的区别在于它们在发现内存处于活动状态后会执行的操作。Go 的垃圾回收器使用标记清除技术，这意味着为了追踪其进度，垃圾回收器会将遇到的值`标记`为活动状态。追踪完成后，垃圾回收器会遍历堆中的所有内存，并将所有未被标记的内存释放出来供分配。这个过程称为`清除`。

你可能熟悉的另一种技术是将对象移动到内存的新区域，并留下一个转发指针，该指针稍后用于更新应用程序的所有指针。我们将以这种方式移动对象的垃圾回收器称为移动型垃圾回收器（Moving GC）；Go 有一个非移动型垃圾回收器。

## GC 循环

由于 Go 的 GC 是一种标记清除式 GC，它大致分为两个阶段：标记阶段和清除阶段。虽然这句话看似同义反复，但它包含一个重要的信息：在所有内存都被追踪之前，无法将内存释放出来供其他对象分配，因为可能仍然存在未扫描的指针，使对象保持存活状态。因此，清除操作必须与标记操作完全分离。此外，当没有与 GC 相关的任务时，GC 也可能完全处于非活动状态。GC 会不断地在清除、关闭和标记这三个阶段之间循环，这被称为 `GC 循环`。在本文档中，我们将 GC 循环理解为从清除开始，然后是关闭，最后是标记。

接下来的几节将着重于帮助用户理解 GC 的开销，以便他们能够根据自身需求调整 GC 参数。

### 理解成本

垃圾回收器 (GC) 本身就是一个复杂的软件，它构建于更加复杂的系统之上。在尝试理解 GC 并调整其行为时，很容易陷入细节的泥沼。本节旨在提供一个框架，用于理解 Go GC 的成本及其调优参数。

首先，考虑以下基于三个简单公理的 GC 成本模型。

1. GC 仅涉及两种资源：物理内存和 CPU 时间。
2. GC 的内存成本包括存活堆内存、标记阶段之前分配的新堆内存以及元数据空间。即使元数据空间与之前的成本成正比，但相比之下仍然很小。

   `第 N 个周期的 GC 内存成本 = 第 N-1 个周期的存活堆内存 + 新堆内存`

   存活堆内存是指上一个 GC 周期确定为活动的内存，而新堆内存是指在当前周期分配的任何内存，这些内存最终可能存活，也可能不存活。在任何给定时间点，有多少内存处于活动状态是程序的属性，GC 无法直接控制。

3. GC 的 CPU 成本被建模为每个周期的固定成本和与存活堆大小成比例的边际成本。

   `第 N 个周期的 GC CPU 时间 = 每个周期的固定 CPU 时间成本 + 每字节的平均 CPU 时间成本 * 第 N 个周期中找到的存活堆内存`

   每个周期的固定 CPU 时间成本包括每个周期发生固定次数的操作，例如为下一个 GC 周期初始化数据结构。这部分成本通常很小，此处列出只是为了完整性。

   GC 的大部分 CPU 成本用于标记和扫描，这部分成本包含在边际成本中。标记和扫描的平均成本取决于 GC 的实现方式，也取决于程序的行为。例如，指针越多，GC 的工作量就越大，因为 GC 至少需要访问程序中的所有指针。对于像链表和树这样的结构，垃圾回收器并行遍历起来也更加困难，从而增加了每字节的平均成本。

   该模型忽略了清扫成本，而清扫成本与堆内存总量成正比，包括已失效的内存（这些内存必须释放出来以供分配）。对于 Go 当前的垃圾回收实现而言，清扫速度远快于标记和扫描，因此其成本可以忽略不计。

该模型简单而有效：它准确地对垃圾回收的主要成本进行了分类。它还告诉我们，垃圾回收器的总 CPU 成本取决于给定时间段内垃圾回收周期的总数。最后，该模型还蕴含了垃圾回收器在时间和空间方面的根本权衡。

为了理解这一点，我们来探讨一个受限但实用的场景：`稳态`。从垃圾回收器 (GC) 的角度来看，应用程序的稳态由以下属性定义：

- 应用程序分配新内存的速率（以字节/秒为单位）是恒定的。

  这意味着，从 GC 的角度来看，应用程序的工作负载随时间推移大致保持不变。例如，对于 Web 服务而言，这意味着请求速率恒定，平均而言，请求的类型也相同，并且每个请求的平均生命周期也大致保持不变。

- GC 的边际成本是恒定的。

  这意味着对象图的统计信息，例如对象大小的分布、指针的数量以及数据结构的平均深度，在每个周期中都保持不变。

让我们来看一个例子。假设某个应用程序处于稳定状态，内存分配速率为 10 MiB/s，而垃圾回收器 (GC) 的内存扫描速率为 100 MiB/CPU-s（此处假设如此）。稳定状态并未对存活堆的大小做任何假设，但为了简化起见，我们假设该应用程序的存活堆始终为 10 MiB。同样为了简化起见，我们假设固定 GC 成本为零。接下来，我们来调整 GC 周期。

假设每个 GC 周期恰好在 1 CPU-s 之后发生。那么，在每个 GC 周期结束时，我们的示例应用程序将分配 10 MiB 的额外内存，从而使堆的总大小达到 20 MiB。并且，在每个 GC 周期中，GC 将花费 0.1 CPU-s 来扫描这 10 MiB 的存活堆，从而产生 10% 的 CPU 开销。请记住，GC 只需要遍历存活堆，而不是整个堆。 （注：恒定的存活堆并不意味着所有新分配的内存都会被销毁。它指的是，在垃圾回收 (GC) 运行后，一部分新旧堆内存会被销毁，最终结果是每个循环中只有 10 MiB 的内存处于存活状态。）

现在假设每次 GC 循环的频率降低，改为每 2 个 CPU 秒一次。那么，在稳定状态下，我们的示例应用程序在每个 GC 循环中将拥有 30 MiB 的总堆大小，因为它会在该时间内分配 20 MiB 的内存。但是，每次 GC 循环，GC 仍然只需要 0.1 个 CPU 秒来扫描这 10 MiB 的存活内存。同样，我们假设存活堆的大小保持不变，无论分配多少内存。这意味着我们的 GC 开销从 10% 降低到 5%，但代价是使用了 50% 的内存。

这种开销的变化就是前面提到的时间/空间权衡。垃圾回收频率是这种权衡的核心：垃圾回收执行频率越高，内存占用就越少，反之亦然。但垃圾回收实际执行的频率是多少呢？在 Go 语言中，何时启动垃圾回收是用户可以控制的主要参数。

### GOGC

从宏观层面来看，GOGC 决定了垃圾回收 (GC) 的 CPU 占用和内存占用之间的平衡。

它的工作原理是：在每次 GC 周期结束后确定目标堆大小，该目标值代表下一个周期的总堆大小。GC 的目标是在总堆大小超过目标堆大小之前完成一个垃圾回收周期。总堆大小定义为上一个周期结束时的存活堆大小，加上自上一个周期以来应用程序分配的任何新的堆内存。同时，目标堆内存定义为：

    `目标堆内存 = 存活堆大小 + (存活堆大小 + GC 根) * GOGC / 100`

例如，考虑一个 Go 程序，其存活堆大小为 8 MiB，goroutine 栈大小为 1 MiB，全局变量指针大小为 1 MiB。那么，当 GOGC 值为 100 时，下次 GC 运行之前将分配 10 MiB 的新内存，即 10 MiB 工作量的 100%，总堆占用量为 18 MiB。当 GOGC 值为 50 时，则为 50%，即 5 MiB。当 GOGC 值为 200 时，则为 200%，即 20 MiB。

    注意：GOGC 仅从 Go 1.18 开始包含根集。此前，它只计算存活堆。通常，goroutine 栈中的内存量很小，存活堆的大小远大于其他 GC 工作量来源，但在程序拥有数十万个 goroutine 的情况下，GC 的判断就出现了偏差。

堆目标值控制着垃圾回收 (GC) 的频率：目标值越大，GC 等待开始下一个标记阶段的时间就越长，反之亦然。虽然精确的公式有助于进行估算，但最好从其基本用途来理解 GOGC：它是一个参数，用于在 GC 的 CPU 和内存权衡中选择一个点。关键在于，`GOGC 值翻倍会使堆内存开销翻倍，而 GC 的 CPU 成本大致减半`，反之亦然。（要了解原因的完整解释，请参阅[附录](https://go.dev/doc/gc-guide#Additional_notes_on_GOGC)。）

    注意：目标堆大小只是一个目标值，GC 周期可能不会正好在该目标值处结束，原因有很多。例如，足够大的堆分配可能会直接超过目标值。然而，在超出本指南目前使用的 [GC 模型](https://go.dev/doc/gc-guide#Understanding_costs)之外的 GC 实现中，还会出现其他原因。更多详细信息，请参阅[延迟部分](https://go.dev/doc/gc-guide#Latency)，但完整的详细信息可以在[其他资源](https://go.dev/doc/gc-guide#Additional_resources)中找到。

GOGC 可以通过 `GOGC` 环境变量（所有 Go 程序都能识别）或 runtime/debug 包中的 [SetGCPercent](https://pkg.go.dev/runtime/debug#SetGCPercent) API 进行配置。

请注意，GOGC 也可以完全关闭（前提是[内存限制](https://go.dev/doc/gc-guide#Memory_limit)不适用），方法是设置 `GOGC=off` 或调用 `SetGCPercent(-1)`。从概念上讲，此设置等同于将 GOGC 的值设置为无穷大，因为触发 GC 之前的新内存量是无限的。

### 内存限制

在 Go 1.19 版本之前，GOGC 是唯一可以用来修改垃圾回收器 (GC) 行为的参数。虽然它作为一种权衡取舍的方式非常有效，但它没有考虑到可用内存是有限的。考虑一下当存活堆大小出现瞬时峰值时会发生什么：由于 GC 会选择一个与该瞬时存活堆大小成比例的总堆大小，因此必须将 GOGC 配置为与峰值存活堆大小成比例，即使在通常情况下，更高的 GOGC 值可以提供更好的权衡。

如果示例工作负载运行在一个可用内存略高于 60 MiB 的容器中，即使其余的 GC 周期有足够的内存来利用额外的内存，GOGC 也无法超过 100。此外，在某些应用程序中，这些瞬态内存峰值可能很少见且难以预测，从而导致偶尔出现、无法避免且可能代价高昂的内存不足情况。

因此，在 Go 1.19 版本中，Go 添加了对设置运行时内存限制的支持。内存限制可以通过所有 Go 程序都识别的 `GOMEMLIMIT` 环境变量进行配置，也可以通过 runtime/debug 包中的 `SetMemoryLimit` 函数进行配置。

此内存限制设置了 Go 运行时可以使用的内存总量的最大值。包含的特定内存集由 [runtime.MemStats](https://pkg.go.dev/runtime#MemStats) 定义，表达式为：

`Sys - HeapReleased`

或者等效地，由 [runtime/metrics](https://pkg.go.dev/runtime/metrics) 包定义：

`/memory/classes/total:bytes - /memory/classes/heap/released:bytes`

由于 Go GC 可以显式控制其使用的堆内存量，因此它会根据此内存限制以及 Go 运行时使用的其他内存量来设置总堆大小。

请注意，在某些 GOGC 值和内存限制下，内存使用峰值会止步于内存限制值，但程序的其余执行仍然遵循 GOGC 设定的总堆大小规则。

这一观察引出了另一个有趣的细节：即使 GOGC 设置为关闭，内存限制仍然有效！事实上，这种特定配置体现了资源利用率的最大化，因为它设置了维持内存限制所需的最低 GC 频率。在这种情况下，程序执行期间堆大小会不断增加以满足内存限制。

现在，虽然内存限制显然是一个强大的工具，但`使用内存限制并非没有代价`，而且也绝不会否定 GOGC 的效用。

考虑一下当存活堆增长到足以使总内存使用量接近内存限制时会发生什么。在上面的稳态可视化图中，尝试关闭 GOGC，然后逐渐降低内存限制，观察会发生什么。请注意，由于垃圾回收器 (GC) 需要不断执行以维持一个不可能达到的内存限制，应用程序的总运行时间将开始无限增长。

这种由于持续的 GC 循环而导致程序无法取得合理进展的情况称为`抖动 (thrashing)`。它尤其危险，因为它实际上会使程序停滞。更糟糕的是，它甚至可能发生在我们试图通过 GOGC 避免的同一情况下：足够大的瞬态堆内存峰值会导致程序无限期停滞！尝试在瞬态堆内存峰值可视化图中降低内存限制（大约 30 MiB 或更低），并注意最糟糕的情况是如何从堆内存峰值开始的。

在许多情况下，无限期停滞比内存不足的情况更糟糕，后者往往会导致程序更快地崩溃。

因此，内存限制被定义为`软限制`。Go 运行时不保证在任何情况下都会维持此内存限制；它只承诺会尽力维持。放宽内存限制对于避免抖动行为至关重要，因为它为垃圾回收器 (GC) 提供了一种出路：允许内存使用量超过限制，从而避免在 GC 中花费过多时间。

其内部工作原理是，GC 会设定一个在一定时间窗口内可使用的 CPU 时间上限（对于 CPU 使用率的极短瞬态峰值，会有一定的滞后性）。目前，该限制设置为大约 50%，时间窗口为 `2 * GOMAXPROCS` CPU 秒。限制 GC CPU 时间的后果是，GC 的工作会被延迟，而 Go 程序可以继续分配新的堆内存，即使超过了内存限制。

50% 的 GC CPU 限制背后的逻辑是基于对拥有充足可用内存的程序的最坏情况影响。如果内存限制配置错误，例如设置得过低，程序最多只会减慢 2 倍，因为 GC 占用的 CPU 时间不能超过其 CPU 时间的 50%。

    注：本页的可视化效果并未模拟 GC CPU 限制。

### 建议用法

虽然内存限制是一个强大的工具，而且 Go 运行时也采取措施来缓解滥用内存限制带来的最坏情况，但谨慎使用它仍然至关重要。以下是一些关于内存限制最有用、最适用的场景以及可能弊大于利的场景的建议。

- 当 Go 程序的执行环境完全由您控制，并且 Go 程序是唯一可以访问某些资源（例如，某种内存预留，如容器内存限制）的程序时，请充分利用内存限制。

  一个很好的例子是将 Web 服务部署到具有固定可用内存的容器中。

  `在这种情况下，一个好的经验法则是预留 5-10% 的额外内存空间，以应对 Go 运行时无法识别的内存来源。`

- 您可以随时根据不断变化的情况实时调整内存限制。

  一个很好的例子是 cgo 程序，其中 C 库需要临时使用大量内存。

- 如果 Go 程序可能与其他程序共享部分有限的内存，并且这些程序通常与 Go 程序解耦，则不要在设置内存限制的情况下关闭 GOGC。相反，应该保留内存限制，因为它有助于抑制不必要的瞬态行为，但应将 GOGC 设置为一个较小的、合理的数值，以适应平均情况。

  虽然尝试为共存程序"预留"内存可能很诱人，但除非这些程序完全同步（例如，Go 程序调用某个子进程并在被调用程序执行期间阻塞），否则结果的可靠性会降低，因为两个程序最终都需要更多内存。让 Go 程序在不需要内存时减少内存使用量，总体上会产生更可靠的结果。此建议也适用于内存过度分配的情况，即运行在同一台机器上的容器的内存限制总和可能超过机器实际可用的物理内存。

- 在部署到您无法控制的执行环境时，请勿使用内存限制，尤其是在程序的内存使用量与其输入成正比的情况下。

  命令行工具或桌面应用程序就是一个很好的例子。如果程序无法预知其输入类型或系统可用内存，就贸然设置内存限制，可能会导致程序崩溃和性能下降。此外，高级用户也可以根据需要自行设置内存限制。

- 如果程序已经接近环境内存限制，就不要为了避免内存溢出而设置内存限制。

  这样做实际上是用严重的应用程序运行速度下降的风险取代了内存溢出的风险，即使 Go 语言已经尽力缓解抖动，这种权衡通常也不可取。在这种情况下，更有效的做法是提高环境的内存限制（然后再根据需要设置内存限制），或者降低 GOGC 值（这比缓解抖动的效果要好得多）。

### 延迟

本文档中的可视化图表模拟了应用程序在垃圾回收器 (GC) 执行期间暂停的情况。确实存在一些 GC 实现采用这种行为，它们被称为"停止世界"GC。

然而，Go GC 并非完全停止世界，它的大部分工作与应用程序并行执行。这主要是为了降低应用程序的延迟，具体来说，就是降低单个计算单元（例如，一个 Web 请求）的端到端持续时间。到目前为止，本文档主要考虑的是应用程序的吞吐量（例如，每秒处理的 Web 请求数）。请注意，[GC 周期](https://go.dev/doc/gc-guide#The_GC_cycle)部分中的每个示例都侧重于执行程序的总 CPU 持续时间。然而，对于例如 Web 服务而言，这种持续时间的意义要小得多。虽然吞吐量对于 Web 服务仍然很重要（即每秒查询数），但通常每个单独请求的延迟更为关键。

就延迟而言，传统的"停止世界"垃圾回收器可能需要相当长的时间来完成标记和清除阶段，在此期间，应用程序（在 Web 服务中，任何正在进行的请求）都无法继续运行。而 Go 垃圾回收器则避免了全局应用程序暂停时间与堆大小成正比，并且核心追踪算法是在应用程序正在运行时执行的。（从算法角度来看，暂停时间与 `GOMAXPROCS` 的相关性更强，但通常主要取决于停止正在运行的 goroutine 所需的时间。）并发回收并非没有代价：在实践中，它通常会导致吞吐量低于等效的"停止世界"垃圾回收器。然而，需要注意的是，更低的延迟并不一定意味着更低的吞吐量，Go 垃圾回收器的性能在延迟和吞吐量方面都随着时间的推移而稳步提升。

Go 当前垃圾回收机制的并发特性并不影响本文档迄今为止讨论的任何内容：所有论述均未依赖于此设计选择。垃圾回收频率仍然是垃圾回收机制在 CPU 时间和内存之间进行权衡以提升吞吐量的主要方式，实际上，它也承担着降低延迟的这一角色。这是因为垃圾回收的大部分开销都发生在标记阶段。

因此，关键在于`降低垃圾回收频率也可能带来延迟的改善`。这不仅适用于通过修改调优参数（例如增加 GOGC 和/或内存限制）来降低垃圾回收频率，也适用于[优化指南](https://go.dev/doc/gc-guide#Optimization_guide)中描述的其他优化方法。

然而，延迟通常比吞吐量更难理解，因为它取决于程序每时每刻的执行情况，而不仅仅是开销的简单叠加。因此，延迟和垃圾回收频率之间的联系并不那么直接。以下列出了一些可能导致延迟的因素，供有兴趣深入研究的读者参考。

1. 垃圾回收器在标记阶段和清除阶段之间转换时会出现短暂的"停止世界"暂停；
2. 由于垃圾回收器在标记阶段会占用 25% 的 CPU 资源，因此会造成调度延迟；
3. 用户 goroutine 会协助垃圾回收器应对高内存分配率；
4. 在垃圾回收器处于标记阶段时，指针写入操作需要额外的处理；以及
5. 正在运行的 goroutine 必须暂停才能扫描其根节点。

除了需要额外处理的指针写入操作外，这些延迟源都可以在[执行追踪](https://go.dev/doc/diagnostics#execution-tracer)中看到。

### 终结器、清理和弱指针

垃圾回收机制利用有限的内存，营造出无限内存的假象。内存会被分配，但不会被显式释放，这使得 API 和并发算法比简单的手动内存管理更加简洁。（一些采用手动内存管理的语言会使用"智能指针"和编译时所有权追踪等替代方法来确保对象被释放，但这些特性已经深深嵌入到这些语言的 API 设计规范中。）

只有存活的对象 — 即可以通过全局变量或 goroutine 中的计算访问的对象 — 才能影响程序的行为。一旦对象变得不可访问（"死亡"），它就可以被垃圾回收器安全地回收。这使得各种垃圾回收器设计成为可能，例如 Go 目前使用的追踪设计。对象的死亡在语言层面上并不是一个可观察的事件。

然而，Go 的运行时库提供了三个打破这种假象的特性：[清理](https://go.dev/pkg/runtime#AddCleanup)、[弱指针](https://go.dev/pkg/weak#Pointer)和[终结器](https://go.dev/pkg/runtime#SetFinalizer)。这些特性都提供了观察和响应对象死亡的方式，对于终结器来说，甚至可以逆转对象死亡。这无疑会使 Go 程序变得复杂，并给垃圾回收器的实现增加额外的负担。尽管如此，这些特性的存在是因为它们在各种情况下都非常有用，Go 程序也一直在使用它们并从中受益。

有关每个特性的详细信息，请参阅其对应的包文档（[runtime.AddCleanup](https://go.dev/pkg/runtime#AddCleanup)、[weak.Pointer](https://go.dev/pkg/weak#Pointer)、[runtime.SetFinalizer](https://go.dev/pkg/runtime#SetFinalizer)）。以下是使用这些特性的一些通用建议、每个特性可能遇到的常见问题概述以及测试这些特性使用情况的建议。

#### 通用建议

- `编写单元测试。`

  清理、弱指针和终结器的确切执行时机难以预测，即使经过多次连续执行，也很容易让人误以为一切正常。但也很容易犯一些不易察觉的错误。为这些机制[编写测试](https://go.dev/doc/gc-guide#Testing_object_death)可能比较棘手，但鉴于它们的使用非常隐蔽，测试就显得尤为重要。

- `避免在典型的 Go 代码中直接使用这些特性。`

  这些是底层特性，存在一些微妙的限制和行为。例如，无法保证清理或终结器会在程序退出时执行，甚至根本无法保证它们会执行。API 文档中冗长的注释应该被视为一种警告。绝大多数 Go 代码并不会直接受益于这些特性，它们的作用仅限于间接使用。

- `将这些机制的使用封装在一个包中。`

  尽可能避免将这些机制的使用泄露到包的公共 API 中；提供能够有效防止用户误用的接口。例如，与其要求用户对某些 C 分配的内存进行清理以释放它，不如编写一个包装包并将此细节隐藏在内部。

- `限制对具有终结器、清理器和指向创建并应用它们的包的弱指针的对象进行访问。`

  这一点与前一点相关，但值得特别强调，因为它是一种以更不容易出错的方式使用这些特性的强大模式。例如，[unique包](https://go.dev/pkg/unique)在底层使用了弱指针，但完全封装了弱指针指向的对象。应用程序的其他部分永远无法修改这些值，它们只能通过 [`Value` 方法](https://go.dev/pkg/unique#Handle.Value)复制，从而为包用户保留了无限内存的假象。

- `尽可能确定性地清理非内存资源，终结器和清理器作为备选方案。`

  清理器和终结器非常适合内存资源，例如外部分配的内存（例如来自 C 的内存）或对 mmap 映射的引用。 C 语言的 malloc 函数分配的内存最终必须由 C 语言的 free 函数释放。将调用 free 函数的终结器附加到 C 内存的包装对象上，是确保 C 内存最终被垃圾回收的合理方法。

  然而，非内存资源（例如文件描述符）往往会受到系统限制，而 Go 运行时通常无法感知这些限制。此外，给定 Go 程序中垃圾回收器的运行时间通常是包作者难以控制的（例如，垃圾回收器的运行频率由 [GOGC](https://go.dev/doc/gc-guide#GOGC) 控制，而 GOGC 可以通过操作符设置为各种不同的值）。这两个因素共同导致清理和终结器并不适合作为释放非内存资源的唯一机制。

  如果您是包作者，并且公开了一个封装了某些非内存资源的 API，请考虑提供一个显式的 API 来确定性地释放资源（例如通过 `Close` 方法或其他类似方法），而不是依赖垃圾回收器通过清理或终结器来释放资源。相反，最好使用清理和终结器作为尽力处理程序员错误的处理程序，要么像 [os.File](https://go.dev/pkg/os#File) 那样清理资源，要么将无法确定性地清理的情况报告给用户。

- `优先使用清理函数而非终结器。`

  历史上，终结器被添加的目的是为了简化 Go 代码和 C 代码之间的接口，并清理非内存资源。其预期用途是将其应用于拥有 C 内存或其他非内存资源的包装对象，以便在 Go 代码使用完毕后释放这些资源。这些原因至少部分解释了为什么终结器的作用域很窄，为什么任何给定对象只能有一个终结器，以及为什么终结器必须附加到对象的第一个字节。这种限制已经阻碍了一些用例。例如，任何希望在内部缓存有关传递给它的对象的某些信息的包，在对象被销毁后都无法清理这些信息。

  更糟糕的是，终结器效率低下且容易出错，因为它们会[复活关联的对象](https://en.wikipedia.org/wiki/Object_resurrection)，以便将其传递给终结器函数（甚至在之后继续存活）。这个简单的道理意味着，如果对象处于引用循环中，它就永远无法被释放，并且支持该对象的内存至少要等到下一次垃圾回收周期才能被重用。

  不过，由于终结器会复活对象，因此它们的执行顺序比清理器更明确。正因如此，终结器在清理具有复杂销毁顺序要求的结构体时仍然可能有用（但很少见）。

  但在 Go 1.24 及更高版本中，对于所有其他用途，我们建议您使用清理器，因为它们比终结器更灵活、更不容易出错且效率更高。

#### 常见清理问题

- 带有清理操作的对象必须无法从清理函数访问（例如，通过捕获的局部变量）。否则，对象将无法被回收，清理操作也无法执行。

```go
    f := new(myFile)
    f.fd = syscall.Open(...)
    runtime.AddCleanup(f, func(fd int) {
        syscall.Close(f.fd) // Mistake: We reference f, so this cleanup won't run!
    }, f.fd)
```

- 带有清理操作的对象不能通过清理函数的参数访问。这将阻止对象被回收，并防止清理操作运行。

```go
    f := new(myFile)
    f.fd = syscall.Open(...)
    runtime.AddCleanup(f, func(f *myFile) {
        syscall.Close(f.fd)
    }, f) // Mistake: We reference f, so this cleanup wouldn't ever run. This specific case also panics.
```

- 终结器具有明确的执行顺序，但清理操作则没有。清理操作也可以并发执行。
- 长时间运行的清理操作应该创建一个 goroutine，以避免阻塞其他清理操作的执行。
- `runtime.GC` 不会等待不可达对象的清理操作执行完毕，而只会等待所有清理操作都进入队列。

#### 常见的弱指针问题

- 弱指针可能会在意外的情况下从其 `Value 方法`返回 `nil`。务必始终使用 `nil` 检查来保护对 `Value 方法`的调用，并准备备用方案。

- 当弱指针用作映射键时，它们不会影响映射值的可达性。因此，如果弱指针映射键指向的对象也可以从映射值访问，则该对象仍然被认为是可达的。

#### 常见的终结器问题

- 附加了终结器的对象不能通过任何路径从自身访问（换句话说，它们不能处于引用循环中）。这将阻止对象被回收，并阻止终结器运行。

```go
    f := new(myCycle)
    f.self = f // Mistake: f is reachable from f, so this finalizer would never run.
    runtime.SetFinalizer(f, func(f *myCycle) {
        ...
    })
```

- 带有终结器的对象不能从终结器函数直接访问（例如，通过捕获的局部变量）。这将阻止对象被回收，并防止终结器运行。

```go
    f := new(myFile)
    f.fd = syscall.Open(...)
    runtime.SetFinalizer(f, func(_ *myFile) {
        syscall.Close(f.fd) // Mistake: We reference the outer f, so this cleanup won't run!
    })
```

- 带有终结器的引用链（例如链表中的对象）至少需要与链中对象数量相同的垃圾回收周期才能清理完毕。务必保持终结器浅层！

```go
    // Mistake: reclaiming this linked list will take at least 10 GC cycles.
    node := new(linkedListNode)
    for range 10 {
        tmp := new(linkedListNode)
        tmp.next = node
        node = tmp
        runtime.SetFinalizer(node, func(node *linkedListNode) {
            ...
        })
    }
```

- 避免在包边界处返回的对象上放置终结器。这会导致包的用户调用 `runtime.SetFinalizer` 来修改返回对象的终结器，而这种行为可能会被包的用户依赖，造成意想不到的后果。
- 长时间运行的终结器应该创建一个新的 goroutine，以避免阻塞其他终结器的执行。
- `runtime.GC` 不会等待不可达对象的终结器执行完毕，而只会等待它们全部进入队列。

使用这些特性时，编写测试用例有时会比较棘手。以下是一些编写健壮测试用例的技巧。

- 避免将此类测试与其他测试并行运行。尽可能提高确定性，并随时掌握对象的状态，对测试结果大有裨益。
- 在进入测试时，使用 `runtime.GC` 建立基线。使用 `runtime.GC` 强制弱指针为 `nil`，并将清理和终结器加入队列以待执行。
- `runtime.GC` 不会等待清理和终结器执行完毕，它只会将它们加入队列。

  为了编写尽可能健壮的测试，请在测试中注入一种阻塞清理或终结器的方法（例如，从测试中向清理和/或终结器传递一个可选通道，并在它们执行完毕后写入该通道）。如果这太难或不可能，另一种方法是基于特定的清理后状态为真来触发循环。例如，操作系统测试在一个循环中调用 `runtime.GC`，以检查文件是否已关闭（一旦文件变得不可访问）。

- 如果编写测试来测试终结器的使用情况，并且您有一个使用终结器的对象链，则至少需要测试能够创建的最深链长度的 `runtime.GC` 调用，以确保所有终结器都能运行。
- 使用竞态模式进行测试，以发现并发清理之间以及清理和终结器代码与代码库其余部分之间的竞态条件。

## 关于虚拟内存的说明

本指南主要关注 GC 对物理内存的使用，但经常出现的一个问题是，这究竟意味着什么，以及它与虚拟内存（通常在 `top` 等程序中显示为"VSS"）有何区别。

物理内存是指大多数计算机中实际物理 RAM 芯片内的内存。[虚拟内存](https://en.wikipedia.org/wiki/Virtual_memory)是操作系统提供的对物理内存的抽象，用于将程序彼此隔离。通常，程序也可以保留不映射到任何物理地址的虚拟地址空间。

`由于虚拟内存只是操作系统维护的一种映射，因此进行不映射到物理内存的大型虚拟内存预留通常成本很低。`

Go 运行时通常在以下几个方面依赖于这种虚拟内存成本的视角：

- Go 运行时不会删除它映射的虚拟内存。相反，它使用大多数操作系统提供的特殊操作来显式释放与某些虚拟内存范围关联的物理内存资源。

  这种技术用于显式管理[内存限制](https://go.dev/doc/gc-guide#Memory_limit)，并将 Go 运行时不再需要的内存归还给操作系统。Go 运行时也会在后台持续释放它不再需要的内存。更多信息请参阅[其他资源](https://go.dev/doc/gc-guide#Additional_resources)。

- 在 32 位平台上，Go 运行时会预先为堆预留 128 MiB 到 512 MiB 的地址空间，以减少内存碎片问题。
- Go 运行时在实现一些内部数据结构时会使用大量的虚拟内存地址空间预留。在 64 位平台上，这些数据结构通常至少占用约 700 MiB 的虚拟内存。在 32 位平台上，它们的占用量可以忽略不计。

因此，诸如 `top` 命令中的"VSS"之类的虚拟内存指标通常对理解 Go 程序的内存占用量没有太大帮助。相反，应关注"RSS"及类似指标，这些指标能更直接地反映物理内存使用情况。

## 优化指南

### 识别成本

在尝试优化 Go 应用程序与垃圾回收器 (GC) 的交互方式之前，首先要确定 GC 是否确实是一项主要成本。

Go 生态系统提供了许多用于识别成本和优化 Go 应用程序的工具。有关这些工具的简要概述，请参阅[诊断指南](https://go.dev/doc/diagnostics)。本文将重点介绍其中一部分工具，并阐述合理的应用顺序，以便了解 GC 的影响和行为。

#### 1. CPU性能分析

[CPU性能分析](https://pkg.go.dev/runtime/pprof#hdr-Profiling_a_Go_program)是一个很好的起点。CPU性能分析可以概览CPU时间的消耗情况，但对于非专业人士来说，可能难以确定垃圾回收器（GC）在特定应用程序中所扮演的角色。幸运的是，理解GC的作用主要在于了解`runtime`包中不同函数的含义。以下列出了一些有助于解读CPU性能分析的函数。

请注意，以下列出的函数并非叶子函数，因此它们可能不会出现在`pprof`工具的默认`top`命令列表中。建议使用`top -cum`命令或直接对这些函数使用`list`命令，并重点关注累计百分比列。

  - `runtime.gcBgMarkWorker`：后台标记工作程序goroutine的入口点。此处的耗时与GC频率以及对象图的复杂性和大小成正比。它代表了应用程序在标记和扫描上花费的时间基准。

    请注意，在这些 goroutine 中，您会发现对 `runtime.gcDrainMarkWorkerDedicated`、`runtime.gcDrainMarkWorkerFractional` 和 `runtime.gcDrainMarkWorkerIdle` 的调用，它们指示工作线程类型。在 Go 应用程序中，如果大部分时间处于空闲状态，Go GC 会使用额外的（空闲的）CPU 资源来更快地完成其任务，这由 `runtime.gcDrainMarkWorkerIdle` 符号指示。因此，此处的 CPU 时间可能占到 Go GC 认为空闲 CPU 资源的很大一部分。如果应用程序变得更加活跃，空闲工作线程的 CPU 时间将会下降。这种情况发生的一个常见原因是，如果应用程序完全在一个 goroutine 中运行，但 `GOMAXPROCS` > 1。

  - `runtime.mallocgc`：堆内存分配器的入口点。此处累计花费的时间较大（>15%）通常表示分配了大量内存。

  - `runtime.gcAssistAlloc`：函数 goroutine 会进入此函数，贡献部分时间协助 GC 进行扫描和标记。此处累计花费的时间过多（>5%）表明应用程序的内存分配速度可能超过了 GC 的处理速度。这表明 GC 的影响非常显著，同时也代表了应用程序花费在标记和扫描上的时间。请注意，此操作包含在 `runtime.mallocgc` 调用树中，因此也会增加该调用树的占用时间。

#### 2. 执行追踪

虽然 CPU 分析非常适合识别时间总体消耗情况，但它们对于指示更微妙、罕见或与延迟相关的性能开销的作用较小。另一方面，执行追踪可以深入了解 Go 程序执行过程中的短窗口。它们包含与 Go GC 相关的各种事件，可以直接观察特定的执行路径，以及应用程序如何与 Go GC 交互。所有追踪到的 GC 事件都会在追踪查看器中清晰地标示出来。

有关如何开始使用执行追踪，请参阅 [`runtime/trace` 包的文档](https://pkg.go.dev/runtime/trace)。

#### 3.GC 追踪

当其他方法都无效时，Go GC 提供了一些特定的追踪信息，可以更深入地了解 GC 行为。这些追踪信息始终直接打印到`标准错误输出 (STDERR)`，每个 GC 周期输出一行，并通过所有 Go 程序都识别的 `GODEBUG` 环境变量进行配置。它们主要用于调试 Go GC 本身，因为它们需要对 GC 的具体实现有所了解，但有时也有助于更好地理解 GC 行为。

核心 GC 追踪通过设置 `GODEBUG=gctrace=1` 启用。此追踪生成的输出记录在运行时包文档的环境变量部分。

一个名为"pacer 追踪"的补充 GC 追踪提供了更深入的信息，通过设置 `GODEBUG=gcpacerrace=1` 启用。解释此输出需要了解 GC 的"pacer"（参见[其他资源](https://go.dev/doc/gc-guide#Additional_resources)），这超出了本指南的范围。

### 减少堆内存分配

降低垃圾回收 (GC) 成本的一种方法是减少 GC 需要管理的内存值数量。下文介绍的技术可以显著提升性能，因为正如 [GOGC 部分](https://go.dev/doc/gc-guide#GOGC)所示，Go 程序的内存分配率是影响 GC 频率（本指南使用的关键成本指标）的主要因素。

#### 堆内存分析

在[确定垃圾回收器 (GC) 是造成大量开销的因素](https://go.dev/doc/gc-guide#Identifying_costs)后，消除堆内存分配的下一步是找出大部分内存分配的来源。为此，内存分析（实际上是堆内存分析）非常有用。请参阅[相关文档](https://pkg.go.dev/runtime/pprof#hdr-Profiling_a_Go_program)了解如何开始使用。

内存分析描述了程序中堆内存分配的来源，并通过分配点的堆栈追踪信息进行识别。每个内存分析可以从四个方面细分内存使用情况：

- `在用对象 (inuse_objects)` — 细分当前存活对象的数量。
- `在用空间 (inuse_space)` — 按字节细分存活对象占用的内存量。
- `已分配对象 (alloc_objects)` — 细分自 Go 程序开始执行以来已分配的对象数量。
- `已分配空间 (alloc_space)` — 细分自 Go 程序开始执行以来已分配的总内存量。

可以通过 `pprof` 工具的 `-sample_index` 标志或在交互式使用该工具时使用 `sample_index` 选项来切换堆内存的不同视图。

  注意：默认情况下，内存分析仅对部分堆对象进行采样，因此不会包含每次堆内存分配的信息。但这足以找到热点区域。要更改采样率，请参阅 [`runtime.MemProfileRate`](https://pkg.go.dev/runtime#pkg-variables)。

为了降低 GC 成本，`alloc_space` 视图通常是最有用的，因为它直接对应于内存分配率。此视图会指出能够带来最大收益的内存分配热点区域。

#### 逃逸分析

一旦借助[堆分析](https://go.dev/doc/gc-guide#Heap_profiling)识别出候选的堆分配位置，如何才能将其排除呢？关键在于利用 Go 编译器的逃逸分析功能，让 Go 编译器为这些内存找到更高效的替代存储位置，例如 goroutine 栈。幸运的是，Go 编译器能够描述它决定将 Go 值逃逸到堆的原因。有了这些信息，接下来只需重新组织源代码以改变分析结果（这通常是最难的部分，但超出了本指南的范围）。

至于如何访问 Go 编译器逃逸分析的信息，最简单的方法是通过 Go 编译器支持的调试标志，该标志以文本格式描述它对某个包应用或未应用的所有优化。这包括值是否被逃逸。尝试以下命令，其中 `[package]` 是某个 Go 包的路径。

```sh
$ go build -gcflags=-m=3 [package]
```

此信息也可以在支持 LSP 的编辑器中以叠加层的形式显示；它以代码操作的形式呈现。例如，在 VS Code 中，调用 "Source Action... > Show compiler optimization details" 命令即可启用当前包的诊断信息。（您也可以运行 "Go: Toggle compiler optimization details" 命令。）使用此配置设置来控制要显示的注解：

  1. 通过将 [`ui.diagnostic.annotations` 设置为 "include `escape`"](https://github.com/golang/vscode-go/wiki/settings#uidiagnosticannotations) 来启用转义分析的叠加层。

最后，Go 编译器以机器可读 (JSON) 格式提供此信息，可用于构建其他自定义工具。有关更多信息，请参阅 [Go 源代码中的文档](https://cs.opensource.google/go/go/+/master:src/cmd/compile/internal/logopt/log_opts.go;l=25;drc=351e0f4083779d8ac91c05afebded42a302a6893)。

### 特定于实现的优化

Go GC 对活动内存的分布情况非常敏感，因为对象和指针的复杂图既会限制并行性，也会增加 GC 的工作量。因此，GC 包含一些针对特定常见结构的优化。以下列出了对性能优化最直接有效的方法。

注意：应用以下优化可能会因模糊代码意图而降低代码可读性，并且可能无法在 Go 版本更新后仍然有效。建议仅在最关键的地方应用这些优化。您可以使用["成本识别"部分](https://go.dev/doc/gc-guide#Identifying_costs)中列出的工具来确定这些关键位置。

- 无指针值与其他值隔离。

  因此，对于并非绝对需要指针的数据结构，移除指针可能是有利的，因为这可以降低垃圾回收器 (GC) 对程序的缓存压力。这样一来，依赖索引（indices）而非指针（pointer）值的数据结构，虽然类型化程度较低，但性能可能更好。只有当对象图非常复杂，且 GC 花费大量时间进行标记和扫描时，这样做才值得。

- GC 会在值中的最后一个指针处停止扫描。

  因此，对于结构体类型的值，将指针字段分组到值的开头可能是有利的。只有当应用程序花费大量时间进行标记和扫描时，这样做才值得。 （理论上编译器可以自动完成此操作，但尚未实现，结构体字段的排列方式与源代码中的写法一致。）

此外，垃圾回收器 (GC) 几乎必须与它遇到的每个指针交互，因此，例如，使用切片索引而不是指针，可以帮助降低 GC 成本。

### Linux 透明大页 (THP)

当程序访问内存时，CPU 需要将其使用的[虚拟内存](https://go.dev/doc/gc-guide#A_note_about_virtual_memory)地址转换为指向其尝试访问的数据的物理内存地址。为此，CPU 会查询"页表（page table）"，这是一种由操作系统管理的表示虚拟内存到物理内存映射的数据结构。页表中的每个条目代表一个不可分割的物理内存块，称为"页（page）"，因此得名。

透明大页（Transparent huge pages, THP）是 Linux 的一项特性，它透明地将支持连续虚拟内存区域的物理内存页替换为更大的内存块，称为"大页（huge pages）"。通过使用更大的内存块，表示同一内存区域所需的页表条目更少，从而缩短了页表查找时间。然而，如果系统只使用了大页的一小部分，那么更大的内存块意味着更多的浪费。

在生产环境中运行 Go 程序时，在 Linux 上启用透明大页 (THP) 可以提高吞吐量并降低延迟，但会增加内存使用量。堆内存较小的应用程序通常无法从 THP 中获益，并且最终可能会占用大量额外内存（高达 50%）。但是，堆内存较大的应用程序（1 GiB 或更大）通常可以获益良多（吞吐量提升高达 10%），而内存开销却非常少（1-2% 或更少）。无论哪种情况，了解 THP 设置都非常有用，并且始终建议进行实验。

可以通过修改 `/sys/kernel/mm/transparent_hugepage/enabled` 文件在 Linux 环境中启用或禁用透明大页。更多详细信息，请参阅[官方 Linux 管理指南](https://www.kernel.org/doc/html/next/admin-guide/mm/transhuge.html)。如果您选择在 Linux 生产环境中启用透明大页，我们建议为 Go 程序进行以下额外设置。

- 将 `/sys/kernel/mm/transparent_hugepage/defrag` 设置为 `defer` 或 `defer+madvise`。

  此设置控制 Linux 内核将普通页面合并成大页面的积极程度。`defer` 指示内核延迟合并大页面，并在后台执行。更积极的设置可能会导致内存受限系统出现停顿，并且通常会增加应用程序的延迟。`defer+madvise` 与 `defer` 类似，但对系统上其他显式请求大页面并需要它们来提升性能的应用程序更友好。

- 将 `/sys/kernel/mm/transparent_hugepage/khugepaged/max_ptes_none` 设置为 `0`。

  此设置控制 Linux 内核守护进程在尝试分配大页面时可以分配的额外页面数量。默认设置为最积极，并且通常会[撤销 Go 运行时为将内存返回给操作系统所做的工作](https://bugzilla.kernel.org/show_bug.cgi?id=93111)。在 Go 1.21 之前，Go 运行时尝试减轻默认设置的负面影响，但这会增加 CPU 开销。从 Go 1.21 及更高版本和 Linux 6.2 及更高版本开始，Go 运行时不再修改大页状态。

  如果您在升级到 Go 1.21.1 或更高版本时遇到内存使用量增加的问题，请尝试应用此设置；它很可能可以解决您的问题。作为另一种解决方法，您可以调用带有 `PR_SET_THP_DISABLE` 参数的 [Prctl 函数](https://go.dev/pkg/golang.org/x/sys/unix#Prctl)来在进程级别禁用大页，或者您可以设置 `GODEBUG=disablethp=1`（将在 Go 1.21.6 和 Go 1.22 中添加）来禁用堆内存的大页。请注意，`GODEBUG` 设置可能会在未来的版本中移除。

## 附录

### 关于 GOGC 的补充说明

[GOGC 部分](https://go.dev/doc/gc-guide#GOGC)指出，将 GOGC 值加倍会使堆内存开销加倍，但会使 GC CPU 成本减半。为了理解其中的原因，让我们从数学角度进行分析。

首先，堆目标设置了堆总大小的目标值。然而，该目标主要影响新的堆内存，因为存活堆对于应用程序至关重要。

```txt

  目标堆内存 = 存活堆内存 + (存活堆内存 + GC 根内存) * GOGC / 100

  总堆内存 = 存活堆内存 + 新增堆内存

                ⇒

  新增堆内存 = (存活堆内存 + GC 根内存) * GOGC / 100

```

由此可见，GOGC 倍增也会使应用程序每个周期分配的新增堆内存量翻倍，这反映了堆内存开销。需要注意的是，`存活堆内存 + GC 根内存`只是 GC 需要扫描的内存量的近似值。

接下来，我们来看一下 GC 的 CPU 开销。总成本可以分解为每个周期的成本乘以垃圾回收频率，并除以时间段 `T`。

```txt

  总 GC CPU 成本 = (每个周期的 GC CPU 成本) * (GC 频率) * T

```

每个周期的 GC CPU 成本可以从 [GC 模型](https://go.dev/doc/gc-guide#Understanding_costs)中推导得出：

```txt

  每个周期的 GC CPU 成本 = (存活堆成本 + GC 根成本) * (每字节成本) + 固定成本

```

`注意，这里忽略了清除阶段的成本，因为标记和扫描阶段的成本占主导地位。`

稳态由恒定的分配率和恒定的每字节成本定义，因此在稳态下，我们可以根据新的堆内存推导出垃圾回收 (GC) 频率：

```txt

  GC 频率 = (分配率) / (新的堆内存) = (分配率) / ((存活堆内存 + GC 根内存) * GOGC / 100)

```

综合以上公式，我们得到总成本的完整公式：

```txt

  总 GC CPU 成本 = (分配率) / ((存活堆内存 + GC 根内存) * GOGC / 100) * ((存活堆内存 + GC 根内存) * (每字节成本) + 固定成本) * T

```

对于足够大的堆（大多数情况下如此），GC 周期的边际成本远大于固定成本。这使得总 GC CPU 成本公式得以显著简化。

```txt

  总 GC CPU 成本 = (分配率) / (GOGC / 100) * (每字节成本) * T

```

从这个简化的公式可以看出，如果 GOGC 翻倍，总 GC CPU 成本就会减半。（请注意，本指南中的可视化模拟的是固定成本，因此 GOGC 翻倍时，它们报告的 GC CPU 开销并不会正好减半。）此外，GC CPU 成本主要取决于分配率和每字节内存扫描成本。有关如何具体降低这些成本的更多信息，请参阅[优化指南](https://go.dev/doc/gc-guide#Optimization_guide)。

注意：存活堆的大小与 GC 实际需要扫描的内存量之间存在差异：相同大小的存活堆，如果结构不同，则会导致不同的 CPU 成本，但内存成本相同，从而导致不同的权衡。这就是为什么堆的结构是稳态定义的一部分。堆目标应该只包含可扫描的存活堆，这样更能近似地反映垃圾回收器需要扫描的内存，但当可扫描的存活堆很小，而存活堆本身很大时，这会导致退化行为。
